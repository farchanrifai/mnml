## Source-supported follow-up plan

1. **P1 — verify and then coordinate sidebar/panel completion with actual geometry.** `App.swift:540` delays room settlement by 0.42 seconds, while `App.swift:763` restores the mirrored edge after 0.45 seconds and `Stage.swift:66` then fades the covering ground for 0.3 seconds. Generation counters prevent stale final updates, but the timers do not prove the sidebar/panel has settled after reversal, resize or main-thread delay. Record opening, closing and immediate reversal in both layouts, page-under mode and Ask side-panel mode. If mismatch reproduces, drive room/edge settlement from completion of the actual animated width/height, with interruption guards. A completion attached only to the nonanimatable `sliding` Bool would not track sidebar movement and is not a valid replacement. Preserve fade-before/alongside-movement intent and end the fade against settled chrome. Apple's SwiftUI completion API is the appropriate existing feature once actual geometry owns the transition: [Animations](https://developer.apple.com/documentation/swiftui/animations), [AnimationCompletionCriteria](https://developer.apple.com/documentation/swiftui/animationcompletioncriteria).

2. **P2 — retain the chosen per-frame layout unless an app-side controlled test demonstrates a better option.** `App.swift:358–363` follows left sidebar and right panel widths on every frame. `docs/mnml/sidebar-slide.md` records that the user chose this implementation and documents the dark-edge/reflow tradeoff. The snapshot alternative has its own doubled-edge and stale-video risks. Use a local fixed-content fixture and record app frame/presentation timings for left sidebar, right Ask panel and their combined reversal. Do not blame page/WebKit performance or retune constants from screenshots alone. Accept the change only with no blank/doubled edge, correct input hit targets, no final geometry jump and stable video.

3. **P2 — measure long-list layout before adding laziness.** The sidebar uses an eager `VStack` (`Side.swift:488–516`) and measures every row through `RowFrames` (`Side.swift:519`) for selection, drag targets and window drag areas. Entry construction scans tabs and calls group-member scans (`Side.swift:474–481`); drag rebuilding does additional scans (`Side.swift:667–689,768–819`). Compare 10/50/200 tab and grouped-tab fixtures in an isolated profile, tracing SwiftUI body/layout work. First deduplicate repeated pure scans if measured; virtualize only if remaining cost warrants it. A blind `LazyVStack` change can break row geometry, reorder, active-row scrolling and sidebar arrival (the eager pin grid's reason is documented at `Side.swift:894–899`).

4. **P2 — sidebar resize and drag lifecycle QA.** The edge pushes/pops a resize cursor on hover (`Side.swift:200–202`) but has no corresponding disappearing-view cleanup. Reproduce hiding the sidebar, entering full screen and closing a window while the pointer rests on the edge; if the resize cursor remains, track the edge's hover state and pop only the cursor that view pushed. Also expose a labelled adjustable width action or native equivalent for keyboard/VoiceOver resizing; current drag/double-click affordances (`Side.swift:193–214`) are pointer-only. Add the alternative without changing the existing 188–440 point bounds or reset behavior.

5. **P2 — make sidebar tab actions fully accessible.** Pins and rows use `OneClick` or tap gestures and visually indicated live selection (`Side.swift:919–978,982–1170`). Audit them with VoiceOver and Full Keyboard Access; ensure each tab announces title/selected state and offers select, close, mute and pinned-home actions without hovering. Prefer native button semantics where nested controls allow it; otherwise use named accessibility actions and selection traits. Keep current menus/shortcuts and drag behavior. Shared Door labels implemented above are only the first part of this work.

6. **P2 — drag dwell must belong to one drag.** The delayed merge callback (`Side.swift:782–787`) checks candidate identity and `held != nil`, but has no drag-generation token. Ending a drag and quickly starting another over the same tab can satisfy an older callback, shortening the new drag's intended dwell. Reproduce with deterministic drag events; then invalidate a generation token on candidate change and drag end and test the rapid repeated-target case.

7. **P2 — transparency/contrast and narrow-window review.** `TopGlass` uses custom backdrop blur (`Under.swift:90–132`), while standard sidebar material is native. Verify Reduce Transparency and Increase Contrast in each material path, together with light/dark/custom tints, inactive windows and 640-point minimum window width. If the custom path ignores the system preference, select an opaque ground via the SwiftUI accessibility environment; do not add another visual-effect dependency or periodic page snapshots. Verify combined sidebar + Ask width leaves useful content before defining any new automatic-collapse rule.

## Existing behavior worth retaining

- `Motion` already centralizes spring/easing policy and reads the macOS Reduce Motion setting (`Design.swift:150–171`); `Shake` itself returns identity when reduced (`Design.swift:223`). Targeted bypass fixes reuse this.
- `Fold` cancels pointer timers on disappearance, uses a dwell/grace rather than responding to every crossing, and keeps edit fields visible (`Fold.swift:69–92,133–144,289–340`). Its traffic-light animation reads the presentation layer and uses a generation guard for rapid reversals (`Fold.swift:381–441`).
- `SpaceSwipe.moved` returns before its interactive spring when reduced (`SpaceSwipe.swift:181,204`); space-switch completion already uses ticket guards and native completion callbacks (`SpaceAppearance.swift:85–121`). Do not blanket-remove meaningful direct gesture feedback.
- `StageView` owns one weak displayed page and reconciles actual view ownership during layout (`Stage.swift:307–313,413–475`). Preserve that instead of adding duplicated page/state bookkeeping.
- `Under.cover` avoids repeating unchanged insets (`Under.swift:28–29`), and native visual materials follow window activation (`Design.swift:241–257`). Avoid changing engine or inset behavior in this app audit.

## Running-app acceptance checklist

Run only in an isolated test app/profile; preserve the main/installed app and normal profile.

- Sidebar/strip: open/close, switch placement, fold/peek, drag width, reset width, reverse before settling, repeat while resizing. Test 640×420, normal and full-screen windows.
- Ask/docked panel: open/close both sides with the sidebar present/hidden; switch tabs while open; rapid reversal; float/full modes. Check composer versus page focus.
- Reduce Motion: repeat all above plus swipe history selection, cover dismissal and invalid-address feedback. No automatic slide/scale/shake, no 0.45-second mirror blackout, controls and focus work immediately.
- Focus: close address field then reopen it or open Settings/Import/What's New before the pending page focus callback; type without clicking; page receives typing again when overlays are dismissed. Repeat with find, tab renaming and different windows.
- Page placement: floating video/PiP and full-screen enter/exit, active-tab changes, docked inspector and split transitions. Page remains visible and responds at the visible hit target.
- VoiceOver/keyboard: navigation icon labels, tab title/selected state, sidebar width, hover-only close/mute/home actions, modal focus, and complete shortcut handling without selecting a hidden tab behind a modal.
- Performance evidence: record repeatable fixture and starting profile, use a Release app, distinguish app main-thread/UI/layout time from excluded page/engine work, keep the same window dimensions and effect settings for A/B. Any frame budget claim requires measured data at the display's refresh rate.
